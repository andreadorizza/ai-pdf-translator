# Build on PDFMathTranslate instead of our own write-back

PDFMathTranslate (pdf2zh) already reads PDFs, finds the layout and writes the translation into the original boxes, and since September 2026 it OCRs scanned pages with Tesseract. We use it for layout and write-back, send generic fixes upstream (Lao and other Tesseract language codes, OCR for pages whose text layer has no letters of the source script, script models such as `script/Lao`) and propose an "external translations" option, so an agent's subagents can translate whole batches. Our repo keeps only what PDFMathTranslate lacks: the second OCR reading, doubts, scan check, term list, batches, review list, self-test and the agent skills.

We chose this over our own write-back because the user prefers to contribute to an existing project rather than rebuild it, and PDFMathTranslate also handles figures, tables, formulas, fonts and bilingual output, which our pilot did not test. On the decree (2026-11-19, `eval/pdf2zh/RESULTS.md`) it scored chrF++ 52 with Google Translate (55 with our OCR models) against our pilot's 66, failed on `-li lo` and on a page with a broken text layer, and crashed in font subsetting; those are the parts we fix upstream or replace. Issues and pull requests are drafted by the agent and posted only after the user approves each one.

Digital pages (a real text layer) also go through PDFMathTranslate's OCR-page path, reading words with PyMuPDF. Its text-page path counts combining marks (Unicode category Mn: Lao, Thai and Khmer vowels and tone marks, Devanagari signs) as formula characters and replaces them with placeholders, which leaves Lao untranslatable. On those pages our writer removes the text of translated paragraphs only, so tables, figure labels and running headers stay as they are.
